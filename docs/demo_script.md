# Healthcare Appointment Mart - Demo Script

**Total Duration:** 5-8 minutes

---

### 0:00–0:40 | Problem Statement
- **Show:** The `README.md` on screen.
- **Say:** "Welcome. This project addresses the DAI-019 requirement: to model healthcare appointments using synthetic data, process it through a robust ETL pipeline, calculate operational no-show metrics, and produce a privacy-safe AI summary. The goal was to build a layered data architecture that strictly protects patient data while still extracting actionable insights."

### 0:40–1:30 | Architecture
- **Show:** The architecture diagram in `docs/architecture.md`.
- **Say:** "Here is the system architecture. We start with raw synthetic CSVs, which are extracted and immediately validated using Pandas-based validation. Valid records move through a Staging layer, into a normalized 3NF Core model, and finally into an Analytical Star Schema. SQL views compute deterministic metrics, which pass through a strict privacy validator before being sent to an AI interface for summarization."

### 1:30–2:20 | Data Model
- **Show:** A quick glance at `sql/02_core/create_core_tables.sql` and `sql/03_mart/create_dim_tables.sql` or the terminal.
- **Say:** "The data model is split into two phases. The Core model is fully normalized to ensure referential integrity—patients, clinics, and appointment types all have strict foreign keys. The Mart model uses a Star Schema. The fact table grain is one row per scheduled appointment. This denormalized structure allows for rapid analytical querying and dimension filtering."

### 2:20–3:10 | ETL Execution
- **Command:** `python -m src.etl.pipeline`
- **Show:** Terminal execution logs.
- **Say:** "Let's run the pipeline. You'll see the extraction phase, followed by strict validation. Any rejected records are quarantined. We then use a truncate-and-reload strategy for reproducibility to load Staging, Core, and Mart. Finally, a reconciliation step proves that the raw appointments made it perfectly to the Fact table."

### 3:10–4:00 | Operational Metrics
- **Show:** `data/processed/metrics_payload.json`
- **Say:** "Once the data is loaded, SQL views calculate the operational metrics. We compute total appointments, completed, cancelled, and no-shows, along with the overall no-show rate. We also break this down by clinic, weekday, time slot, and month to identify specific trends. SQL acts as our authoritative calculation layer."

### 4:00–5:00 | Privacy Boundary + AI Architecture
- **Show:** `src/analytics/metrics.py` and `src/ai/ollama_model.py`.
- **Say:** "This is a critical part of the design. To prevent LLM hallucination, we do not ask the AI to perform calculations. Python precomputes the 'key_findings'—like the highest no-show clinic or month. We also enforce a strict privacy boundary: patient names, emails, and IDs are actively stripped out. The LLM only receives a heavily condensed payload of overall stats and these precomputed key findings."

### 5:00–6:00 | Actual AI Summary
- **Command:** (If Ollama is running) `AI_BACKEND=ollama OLLAMA_MODEL=qwen3:1.7b python -m src.etl.pipeline`
- **Show:** The final AI summary printed in the terminal.
- **Say:** "Here is the final output generated by the local Qwen3 model. In this demonstrated run, the generated summary matched the supplied precomputed findings, and automated tests cover unsupported rankings, missing months, cross-dimension relationships, and privacy violations. The AI is restricted to natural language generation based strictly on provided facts."

### 6:00–6:45 | Tests
- **Command:** `pytest -v`
- **Show:** Test suite execution.
- **Say:** "The project includes a comprehensive test suite. We have dozens of tests passing that cover ETL transformations, data validation, metrics structure, the privacy boundary, and AI faithfulness. We specifically wrote tests to ensure the AI does not fabricate missing months and that the mock AI output remains strictly deterministic."

### 6:45–7:30 | Failure/Edge Case
- **Show:** `tests/test_validation.py` or the `invalid_appointments.csv` fixture.
- **Say:** "We also handle bad data gracefully. Using an intentional failure fixture, we demonstrate that invalid rows—such as missing fields or mismatched dates—are rejected at the validation layer. The pipeline quarantines these bad records without crashing, allowing valid appointments to proceed."

### 7:30–8:00 | Conclusion
- **Show:** The terminal or README.
- **Say:** "In conclusion, this project successfully models healthcare appointments, implements a layered ETL pipeline in PostgreSQL, enforces strict privacy constraints, and provides a 100% faithful, precomputed AI summary of operational metrics. Thank you."
